## 1. 系统原理

### 1.1 业务原理

吊牌制造的成本构成是**阶梯式**的：同一规格产品，批量越大、单张成本越低；不同纸张、不同工艺、不同配送地区各有独立的价格阶梯。Excel 报价表将这一阶梯固化为「规格代码 × 批量档位」的二维价格矩阵。本系统的核心原理，就是**将矩阵查询 + 四要素求和 + 毛利换算**这三步人工计算自动化。

### 1.2 技术原理

| 原理 | 说明 |
|------|------|
| 单文件架构 | 全部逻辑打包进一个 HTML，浏览器打开即运行，无服务器、无构建、无数据库依赖 |
| CDN 数据交换 | SheetJS（xlsx 0.20.1）在浏览器端解析/生成 xlsx 二进制，数据不离开用户设备 |
| localStorage 持久化 | 浏览器本地存储客户配置，刷新不丢失 |
| 静态部署 | Cloudflare Pages 只做静态文件托管，push 触发构建 |
| 降级机制 | `typeof XLSX === "undefined"` 检测 CDN 加载失败，给出可读错误提示 |

### 1.3 核心设计决策（铁律的形成）

| 决策 | 触发背景 | 技术实现 |
|------|----------|----------|
| 源数据不可变 | 修改 Excel 有误改风险，且无法追溯 | 解析只读，内存操作 |
| 空值不补 0 | 补 0 会把「无此档」误报为「免费」 | 空值 → `null` → UI 占位徽章 |
| 精确档位匹配 | 向上取档会把 500 张价错报给 2500 张客户 | `hasExactTier()` 只认精确档位 |
| 规格向上匹配 | 印刷品规格必须物理覆盖成品面积 | `matchSpec()` 取 maxArea ≥ 面积的最小规格 |
| 固定出血 3mm | 印刷裁切需出血，行业标准 3mm | `calcBleedArea()` 统一 (长+3)×(宽+3) |

## 2. 代码结构分析（v4.3）

### 2.1 五区结构

| 区域 | 行范围 | 行数占比 | 职责 | 修改频率 |
|------|--------|----------|------|----------|
| CSS 样式 | 1-1310 | 20.8% | 视觉、布局、响应式、组件 | 低（改 UI 时） |
| HTML 骨架 | 1311-2100 | 12.6% | 页面结构、表单控件 | 低 |
| 数据配置层 | 2101-3810 | 27.2% | 全部价格/配置常量 | 中（换数据时） |
| 计算逻辑层 | 3811-4000 | 3.0% | 核心计算函数 | 极低（受铁律保护） |
| 交互渲染层 | 4001-6285 | 36.4% | DOM、事件、Excel、初始化 | 高（功能迭代主战场） |

**结构评价**：计算逻辑层仅占 3% 且高度稳定，是设计成功之处——核心业务规则与 UI 完全解耦，数据更换不影响计算，计算改动不影响渲染。

### 2.2 数据流

```
┌──────────┐   ┌──────────────┐   ┌────────────┐   ┌──────────────┐
│ 用户输入  │ → │ sheetsState  │ → │ calculate()│ → │ 结果 DOM 渲染 │
│ 档位/纸张 │   │ 纸张配置数组  │   │ 匹配+求和  │   │ 明细+警告+报价 │
│ 尺寸/工艺 │   │              │   │            │   │              │
└──────────┘   └──────────────┘   └────────────┘   └──────────────┘
      ▲                                                      │
      │                    localStorage                     │
      └────────── CUSTOMER_LEVELS / APP_PROFILE ←────────────┘
                            （持久化层）
```

### 2.3 渲染层三大模式

| 模式 | 位置 | 说明 |
|------|------|------|
| 模板字符串 innerHTML | renderPriceTable / renderSheets / renderSnapshots 等 | 用户数据必须 `escapeHtml()` |
| 事件委托/单独绑定 | bindEvents() | select 只绑 change，input 绑 input+change |
| 状态驱动重建 | rebuildPaperUI() | 导入后整树重建 |

## 3. 计算逻辑深度推演

### 3.1 完整示例：350铜版纸 500 张

**输入**：paper1（折扣 1.00），宽 55mm × 长 30mm，500 张，广东省内，不加吊绳。

```
① 面积：singleArea = (55+3) × (30+3) = 58 × 33 = 1914 mm²
② 规格：maxArea ≥ 1914 的最小规格 → code "002"（maxArea 1999）
③ 纸张原价：spec.prices[500] = 20 元
④ 纸张折后价：20 × 1.00 = 20 元
⑤ 工艺：paper1 无工艺 → 0
⑥ 吊绳：rope0 → 0
⑦ 邮费：region1.basePrices[500] = 12；面积 1914 < 2500 → 12 × 0.8 = 9.6
⑧ 成本：20 + 0 + 0 + 9.6 = 29.6
⑨ 报价：普通客户 29.6×1.30 = 38.48
       优质客户 29.6×1.15 = 34.04
       大客户   29.6×1.05 = 31.08
```

### 3.2 边界条件推演

| 场景 | 处理 | 结果 |
|------|------|------|
| 面积 > 10000 mm²（如 110×110） | matchSpec 返回 error | 返回「请与上级联系」，终止计算 |
| 面积无规格覆盖（理论上 maxArea 最大值即上限） | 无候选 | 返回「未找到匹配规格」 |
| 档位缺价（如 702铜版纸 2500 张） | hasExactTier false | 纸张费 null + 警告 |
| 面积 < 2500（如 55×30=1914） | 邮费 × 0.8 | 小面积优惠 |
| 面积 ≥ 2500 | 邮费原价 | 无优惠 |
| 尺寸类型 single/spread | 当前统一按输入长宽计算 | 面积相同（简化实现） |
| 吊绳 rope0 | 全档位 0 | 免费，不产生缺价警告 |

### 3.3 多纸张成本语义

```
paperTotal（折后合计）= Σ 每张纸折后价（各自独立匹配规格/档位）
paperOriginalTotal（折扣前合计）= Σ 每张纸原价
工艺费用 = Σ 所有纸张选中的工艺价格（工艺按纸张绑定）
吊绳/邮费 = 单次（不随纸张数量翻倍）
```

**语义澄清**：纸张数量（sheetCount）指**报价单包含几种纸**，而非每种纸的张数；总批量档位（tier）适用于全部纸张。吊绳/邮费按整体计算一次。

## 4. 可替代方案分析

### 4.1 当前方案 vs 替代方案

| 维度 | 当前（单文件纯前端） | 替代 A：多文件+构建工具 | 替代 B：前后端分离+数据库 |
|------|----------------------|------------------------|--------------------------|
| 部署 | 拖拽/ push 即用 | 需 CI 构建（Vite/webpack） | 需后端运维 |
| 成本 | 0 | 0 | 服务器 + 域名备案 |
| 数据更新 | 改 HTML 内常量/导入 Excel | 改 data.js | 改数据库 |
| 离线可用 | ✅ | ✅（构建后仍静态） | ❌ 依赖接口 |
| 多端同步 | ❌ localStorage 单机 | ❌ | ✅ 云端账号 |
| 安全 | 数据在浏览器，Excel 可下载 | 同左 | 需鉴权体系 |
| 维护 | 6,285 行单文件 | 拆分模块易维护 | 前后端两套代码 |

### 4.2 分阶段替代路线

| 阶段 | 方案 | 适用场景 |
|------|------|----------|
| 现在（测试期） | 保持单文件 + EPHEMERAL_KEYS | 频繁更新数据、无真实用户数据 |
| 试运营 | 单文件 + localStorage 完整持久化 | 有少量用户、无多端需求 |
| 正式运营 | 拆分文件 + Cloudflare D1/KV 同步 | 需多端同步、数据统计 |
| 规模化 | 后端 API + 数据库 + 权限 | 多团队、多报价表、订单管理 |

### 4.3 关键技术替代选择

| 环节 | 当前 | 可替代 | 优劣 |
|------|------|--------|------|
| Excel 解析 | SheetJS 0.20.1 CDN | ExcelJS / 后端解析 / CSV | SheetJS 最轻量；ExcelJS 功能更强但体积大 |
| 存储 | localStorage | IndexedDB / D1 / KV / Supabase | localStorage 最简；IndexedDB 容量大；D1 可同步 |
| 部署 | Cloudflare Pages | Vercel / Netlify / GitHub Pages | Pages 国内可达性好；GitHub Pages 免费但大陆访问差 |
| 框架 | 原生 JS | Vue 3 / React / Svelte | 原生零依赖；Vue 响应式省代码；Svelte 编译期优化 |
| 计算实现 | JS 函数 | Web Worker / 后端计算 | 当前规模无需；大数据量时 Worker 防卡顿 |

## 7. 版本演进方法论总结

### 7.1 演进特征

| 阶段 | 驱动力量 | 产出特征 |
|------|----------|----------|
| 查询 → 计算 | 业务需求升级 | 从查表工具变为报价工具 |
| 硬编码 → Excel 化 | 数据维护成本 | 数据与代码解耦，非技术人员可更新 |
| 补 0 → 占位 | Master 业务铁律 | 数据真实性优先于界面美观 |
| 功能 → 质量 | 安全/性能意识 | XSS 修复、体积治理、事件去重 |
| 单层 → 三级架构 | 扩展性预判 | 小组/报价表/纸张分层，为多租户铺路 |

### 7.2 值得固化的经验

1. **铁律先于功能**：数据真实性规则（不补 0）在 v3.4 确立后，所有后续版本自动继承，避免了返工
2. **核心计算层保护**：计算逻辑仅占 3% 代码量且稳定，UI 频繁变更不影响业务正确性
3. **测试期数据策略**：EPHEMERAL_KEYS 用"每次刷新取最新默认"规避了缓存覆盖问题，是低成本高收益的测试期方案
4. **文档与代码同步**：CHANGELOG + HANDOFF + AGENT-INSTRUCTIONS 三件套保证可交接
5. **部署链路自愈**：空 commit 触发、hash 子域名绕过 DNS 污染等技巧，形成了稳定的部署 playbook
